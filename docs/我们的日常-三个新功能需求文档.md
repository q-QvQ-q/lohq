# “我们的日常”三个新功能需求文档

> 文档版本：V1.0
> 编写日期：2026-09-22
> 文档状态：需求初稿，待确认
> 适用项目：LOHQ 情侣空间

## 1. 项目背景

当前首页“我们的日常”栏目包含“恋爱账单”等快捷入口。本次改版需要下线原“恋爱账单”的产品功能，并新增以下三个情侣共同使用的模块：

1. 情侣点单小店；
2. 打卡评价记录；
3. 未来信件。

三个模块都服务于当前已绑定的情侣关系，数据只允许情侣双方查看和操作。未绑定伴侣的用户可以看到功能介绍和绑定引导，但不能创建双方协作数据。

## 2. 本期目标

- 用“情侣点单小店”替换原“恋爱账单”，通过甜心币和可兑换菜单增加互动感。
- 建立两个人共同维护的地点、酒店、美食体验档案，并支持双方独立评价。
- 支持写下暂时不可见的信件，在指定时间自动解锁，形成共同期待。
- 所有需要双方协作的关键操作都有明确状态、站内通知和结果反馈。

## 3. 名词与统一规则

### 3.1 名词定义

| 名词 | 定义 |
| --- | --- |
| 情侣空间 | 当前用户与已绑定伴侣共同拥有的数据空间 |
| 甜心币 | 点单小店内唯一使用的虚拟币，界面可使用金币图标展示 |
| 个人余额 | 双方各自独立拥有的甜心币数量，互不共用 |
| 加币申请 | 一方提出、另一方审批后才生效的甜心币增加请求 |
| 菜单商品 | 可以用甜心币兑换的内容，例如“做一顿饭”“按摩十分钟” |
| 打卡记录 | 一次地点、酒店、美食或其他体验的共同记录 |
| 双人评价 | 情侣双方针对同一条打卡记录分别填写的评分和文字评价 |
| 未来信件 | 设置开启时间并封存，在开启时间到达后双方才可查看正文的信件 |

### 3.2 通用权限

- 仅情侣双方能够查看共同空间内的数据。
- 用户解绑伴侣后，不得继续查看原情侣空间数据；历史数据保留，不自动转移给新伴侣。
- 重新绑定原伴侣后，可恢复访问原共同数据；绑定其他人时创建新的情侣空间。
- 所有金额、币值和状态变化应记录操作人、操作时间和原因，保证可追溯。
- 涉及余额变化、审批和信件解锁的时间，以服务端时间为准。

## 4. 首页入口调整

### 4.1 “我们的日常”栏目入口

在首页“我们的日常”快捷入口区域进行以下调整：

| 调整 | 入口名称 | 建议说明文案 | 建议路径 |
| --- | --- | --- | --- |
| 替换 | 情侣点单小店 | 用甜心币兑换彼此的小心愿 | `/shop`，也可兼容旧 `/wallet` 并自动跳转 |
| 新增 | 打卡评价 | 收藏我们一起体验过的地方 | `/check-ins` |
| 新增 | 未来信件 | 写给未来某一天的我们 | `/future-letters` |

### 4.2 原“恋爱账单”处理

- 首页不再展示“恋爱账单”入口。
- 原账单页面、账单新增能力及账单统计从产品功能中下线。
- 为避免误删除，旧账单数据本期默认只做归档保留，不直接物理删除。
- 原 `/wallet` 链接建议跳转至“情侣点单小店”，避免旧收藏或历史链接进入失效页面。
- 如后续确认需要彻底删除历史账单数据，应单独执行带备份的数据清理方案。

## 5. 功能一：情侣点单小店

### 5.1 功能目标

情侣双方拥有各自独立的甜心币余额，可以共同维护带分类的兑换菜单。用户使用自己的甜心币点单，系统即时扣币、生成订单并通知对方；任何加币都必须写明理由并取得另一方同意。

### 5.2 页面结构

点单小店首页建议包含：

1. 双方余额卡片；
2. “申请加币”按钮；
3. 菜单分类筛选；
4. 菜单商品列表；
5. 我的订单；
6. 待我处理；
7. 甜心币明细；
8. 菜单管理入口。

### 5.3 甜心币账户

#### 5.3.1 余额展示

- 页面同时展示双方昵称、头像及各自余额。
- 用户只能使用自己的余额点单，不能直接支出伴侣的余额。
- 余额必须为非负整数，不支持小数和负数。
- 新账户初始余额默认为 0；如需初始赠币，应通过系统初始化流水记录。

#### 5.3.2 加币申请

发起人创建加币申请时必须填写：

- 入账对象：自己或对方；
- 甜心币数量：大于 0 的正整数；
- 加币理由：必填，建议 2～100 字；
- 可选凭证：图片，非本期强制项。

业务流程：

1. 一方提交加币申请，状态为“待对方同意”。
2. 另一方收到站内通知，可查看数量、入账对象和理由。
3. 另一方选择“同意”或“拒绝”；拒绝时可填写备注。
4. 同意后，系统只入账一次，并生成不可删除的甜心币流水。
5. 拒绝后不改变余额，申请进入“已拒绝”状态。
6. 发起人可在审批前撤回；审批后不可撤回或重复审批。

状态定义：

`待审批 → 已同意 / 已拒绝 / 已撤回`

防重复规则：

- 审批与入账必须在同一个原子事务中完成。
- 对同一申请重复点击“同意”，只能产生一条入账流水。
- 审批人必须是发起人的当前绑定伴侣，发起人不能审批自己的申请。

### 5.4 菜单与分类

#### 5.4.1 默认分类

- 吃喝：做饭、奶茶、甜品等；
- 陪伴：散步、约会、看电影等；
- 家务：洗碗、收拾房间等；
- 关怀：按摩、抱抱、哄睡等；
- 娱乐：游戏、唱歌、拍照等；
- 其他。

分类支持双方新增、自定义排序、重命名和停用。已有订单引用的分类不得物理删除，只能停用。

#### 5.4.2 菜单商品字段

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 商品名称 | 是 | 1～30 字 |
| 分类 | 是 | 从有效分类中选择 |
| 价格 | 是 | 大于 0 的正整数，单位为甜心币 |
| 商品说明 | 否 | 0～200 字 |
| 封面图 | 否 | 支持一张图片 |
| 提供者 | 是 | 我、伴侣或双方均可提供 |
| 有效状态 | 是 | 上架或下架 |
| 每人限购 | 否 | 可设置每天、每周或总次数限制，后续增强项 |

- 双方均可新增和编辑菜单商品。
- 已产生订单的商品不得物理删除，只能下架。
- 商品改价后，历史订单保留下单时的商品名称、价格和说明快照。

### 5.5 点单流程

1. 用户选择分类并进入商品详情。
2. 页面展示商品信息、价格、提供者、当前个人余额和点单备注输入框。
3. 点击“立即点单”后展示确认弹窗，明确本次扣币数和扣币后的余额。
4. 确认后，系统校验商品仍在售、提供者有效且余额充足。
5. 系统在同一事务中扣除下单人的甜心币、写入支出流水并创建订单。
6. 成功后页面展示明显提示，例如“点单成功，已通知 TA”，同时更新余额和订单列表。
7. 商品提供者收到站内通知；通知可直接进入订单详情。

余额不足时：

- 禁止下单；
- 明确显示“还差 N 枚甜心币”；
- 提供“申请加币”快捷入口。

### 5.6 订单管理

订单建议采用以下状态：

`待接单 → 已接单 → 已完成`

异常分支：

- 待接单时，提供者可以拒绝订单；拒绝后状态为“已拒绝”，系统自动原路退币。
- 待接单时，下单人可以取消订单；取消后状态为“已取消”，系统自动原路退币。
- 已接单后不允许单方面取消；如确需取消，需要双方确认，作为后续增强能力。
- 完成后订单不可删除，可填写完成留言或上传纪念照片，作为后续增强能力。
- 退款必须生成独立的返还流水，不能直接修改或删除原扣币流水。

订单详情至少展示：商品快照、下单人、提供者、价格、备注、当前状态、各状态时间、关联扣币与退款记录。

### 5.7 甜心币明细

- 明细类型包括：审批加币、点单扣币、取消退款、拒单退款、系统调整。
- 每条明细展示变动数量、变动后余额、原因、关联申请或订单、操作时间。
- 普通用户不能编辑或删除流水。
- 支持按收入/支出、成员和时间筛选。

### 5.8 提示与通知

| 事件 | 接收人 | 提示/通知 |
| --- | --- | --- |
| 提交加币申请 | 审批人 | “TA 申请增加 N 枚甜心币，等待你的同意” |
| 加币同意/拒绝 | 发起人 | 告知审批结果和备注 |
| 点单成功 | 下单人 | 页面成功提示，并显示扣币后余额 |
| 收到新订单 | 商品提供者 | “TA 点了「商品名」，快去接单吧” |
| 接单/拒单/完成 | 另一方 | 同步订单状态；拒单时说明已退款 |

### 5.9 验收标准

- 双方看到的是两个独立且准确的余额。
- 未经另一方同意，加币申请不能改变任何人的余额。
- 加币理由为空时不能提交。
- 余额不足、商品下架或提供者无效时不能成功点单。
- 并发或重复点击不会重复扣币、重复加币或创建重复订单。
- 点单成功后余额即时更新，页面有成功提示，提供者收到通知。
- 取消或拒单后，甜心币准确退回且有完整流水。
- 菜单可以按分类筛选，历史订单不受后续商品改名、改价或下架影响。

## 6. 功能二：打卡评价记录

### 6.1 功能目标

记录情侣双方一起去过的地方、住过的酒店、吃过的美食及其他共同体验，保留地址、价格、照片和双方各自的真实评价，形成可查询的共同体验档案。

### 6.2 页面结构

1. 顶部统计：总打卡数、平均评分、最常打卡分类；
2. 分类筛选：地点、酒店、美食、娱乐、旅行、其他；
3. 搜索与排序：按名称、地址搜索；按打卡日期、创建时间、评分、价格排序；
4. 打卡卡片列表；
5. 新建打卡按钮；
6. 待评价入口；
7. 打卡详情页和编辑页。

### 6.3 打卡记录字段

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 名称 | 是 | 1～50 字，例如店名、酒店名、景点名 |
| 分类 | 是 | 地点、酒店、美食、娱乐、旅行、其他 |
| 打卡日期 | 是 | 不晚于当前时间；若支持计划打卡，应另设“想去”状态 |
| 地址 | 是 | 文本地址；地图选点为后续增强项 |
| 总价/人均价 | 否 | 非负数，并明确价格口径 |
| 币种 | 否 | 默认人民币 CNY |
| 照片 | 否 | 支持多张，建议最多 9 张 |
| 共同备注 | 否 | 0～500 字，例如点过的菜、房型、路线 |
| 创建人 | 系统 | 自动记录 |
| 创建/更新时间 | 系统 | 自动记录 |

建议在价格字段中让用户选择“总价”或“人均价”，列表中必须带口径展示，避免歧义。

### 6.4 双人评价

每一条打卡记录关联两份互相独立的个人评价。每位成员只能提交或编辑属于自己的评价，不能代替对方填写。

每份评价包含：

- 综合评分：1～5 星，必填；
- 评价文字：0～500 字；
- 推荐态度：推荐、一般、不推荐；
- 标签：可多选，例如“性价比高”“环境好”“服务好”“适合约会”“会再去”；
- 评价时间和最后修改时间。

展示规则：

- 一方评价后，另一方可以立即看到该评价；本期不采用盲评。
- 详情页并排或分区展示“我的评价”和“TA 的评价”。
- 仅一人评价时，记录状态显示“等待 TA 评价”。
- 两人都评价后，状态显示“双方已评价”，并展示双人平均分。
- 双人平均分为两人综合评分的算术平均值，保留 1 位小数。

### 6.5 创建与编辑流程

1. 任一方创建打卡，填写基础信息，可同时提交自己的评价。
2. 创建成功后通知另一方补充评价。
3. 双方都可编辑共同基础信息；系统记录最后编辑人和更新时间。
4. 每人仅可编辑自己的评价。
5. 删除打卡属于影响双方的操作，需二次确认；建议放入回收站保留 30 天，避免误删。

冲突处理：

- 两人同时编辑共同信息时，提交前校验版本号。
- 若记录已被对方修改，提示用户刷新并确认后再提交，禁止静默覆盖。

### 6.6 列表与详情展示

列表卡片至少展示：

- 封面图或分类图标；
- 名称、分类、打卡日期；
- 地址摘要；
- 价格及“总价/人均”口径；
- 我的评分、TA 的评分或“待评价”；
- 双方已评价时显示平均分。

详情页还应展示全部照片、共同备注、双方评价、创建人与编辑记录。

### 6.7 提示与通知

| 事件 | 接收人 | 提示/通知 |
| --- | --- | --- |
| 新建打卡 | 伴侣 | “TA 记录了「名称」，等你来评价” |
| 一方完成评价 | 尚未评价的一方 | “TA 已评价「名称」，也写下你的感受吧” |
| 双方完成评价 | 双方 | “「名称」的双人评价已完成” |
| 打卡被编辑或删除 | 另一方 | 显示操作者和记录名称 |

### 6.8 空状态与异常状态

- 无记录：展示“把第一次共同体验记录下来”的引导和新建按钮。
- 筛选无结果：展示清除筛选入口。
- 地址或价格缺失：列表以“未填写”展示，不影响其他字段。
- 图片上传失败：保留已填文字，不清空表单，可单独重试。
- 伴侣尚未评价：持续显示待评价状态，但不强制或重复频繁通知。

### 6.9 验收标准

- 用户可按分类浏览并通过名称或地址搜索打卡记录。
- 每条记录能够保存地址、日期、价格口径、共同备注和图片。
- 两人只能编辑自己的评价，不能覆盖对方评价。
- 一人或两人完成评价时，状态与平均分计算准确。
- 新记录创建后，另一方收到一次有效通知。
- 双方同时编辑时不会静默覆盖数据。
- 删除操作有二次确认，并能够在约定保留期内恢复。

## 7. 功能三：未来信件

### 7.1 功能目标

用户可以写一封给未来的信，设置开启时间并封存。封存后，在开启时间到达前，情侣双方都不能查看正文；到达开启时间后，双方才能阅读信件。

### 7.2 页面结构

1. 写一封未来信；
2. 未开启列表；
3. 已开启列表；
4. 信件详情；
5. 草稿箱。

### 7.3 信件字段

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 标题 | 是 | 1～50 字；封存前可编辑 |
| 正文 | 是 | 1～10000 字 |
| 开启时间 | 是 | 必须晚于当前服务端时间，精确到分钟 |
| 写信人 | 系统 | 当前用户 |
| 收信范围 | 系统 | 当前情侣双方 |
| 封面/信纸主题 | 否 | 从预设样式中选择 |
| 附件 | 否 | 图片或音频可作为后续增强项 |
| 创建、封存、开启时间 | 系统 | 自动记录 |

### 7.4 信件状态

`草稿 → 已封存（未到时间） → 已开启`

异常状态：

- 草稿可删除；
- 已封存信件原则上不可编辑正文或开启时间；
- 如允许撤回，应由写信人在开启前发起，并经另一方同意，作为后续增强项；
- 到达开启时间后由系统自动判定为可开启，不依赖用户保持页面在线。

### 7.5 创建与封存流程

1. 用户填写标题、正文和开启时间。
2. 用户可“保存草稿”，草稿仅写信人可见和编辑。
3. 点击“封存信件”时显示确认弹窗，明确提示：封存后直到指定时间，写信人和伴侣都无法查看正文或修改信件。
4. 用户确认后，系统保存信件并切换为“已封存”。
5. 伴侣收到“TA 写了一封未来信”的通知，但不能看到正文。
6. 到达开启时间后，双方收到可开启通知，并可进入详情阅读。

### 7.6 开启前展示规则

- 双方可看到信封卡片，但正文必须由服务端禁止返回，不能只在前端隐藏。
- 卡片可展示：标题、写信人、封存日期、计划开启时间和倒计时。
- 默认允许显示标题；如希望保留更多惊喜，可后续增加“标题也保密”选项。
- 写信人同样不能预览已封存正文。
- 页面刷新、修改本地时间或直接请求接口，都不能提前读取正文。

### 7.7 到时开启规则

- 当前服务端时间达到 `unlock_at` 后，双方均获得读取正文的权限。
- “双方才能查看”定义为：双方在到期后都具备查看权限，不要求两人同时在线或先后点击确认。
- 第一次打开时可播放拆信动效，并记录各自首次阅读时间。
- 若一方先阅读，另一方仍可独立阅读；可以显示“TA 已读”，但不暴露具体在线行为。
- 开启后的信件不可修改正文，可长期保存或由双方共同确认删除。

### 7.8 时间与时区

- 创建时按用户本地时区展示，数据库统一存储 UTC 时间。
- 页面必须同时显示完整日期、时间和时区，例如“2027年1月29日 20:00（北京时间）”。
- 最短封存时长建议为 10 分钟，避免误把当前时间设为开启时间。
- 服务端负责最终到期判断；客户端倒计时只用于展示。

### 7.9 安全与隐私

- 未到开启时间时，查询列表接口不得返回正文字段。
- 正文读取策略必须同时校验：当前用户属于该情侣空间，且服务端时间已到。
- 数据库访问策略不能允许用户绕过页面直接提前读取正文。
- 日志、通知正文和错误信息不得包含信件正文。
- 解绑后双方失去该情侣空间访问权限；重新绑定原伴侣后按通用规则恢复。

### 7.10 提示与通知

| 事件 | 接收人 | 提示/通知 |
| --- | --- | --- |
| 保存草稿 | 写信人 | 页面提示“草稿已保存” |
| 封存成功 | 写信人 | “信件已封存，将在指定时间开启” |
| 新信件封存 | 伴侣 | “TA 给未来写了一封信，开启时间为……” |
| 到达开启时间 | 双方 | “未来的信已到达，现在可以打开了” |
| 一方首次阅读 | 可选通知另一方 | 后续增强，默认不强制通知 |

### 7.11 验收标准

- 草稿仅写信人可见，可继续编辑或删除。
- 封存前必须填写标题、正文和有效的未来时间。
- 封存确认文案明确告知双方到期前都无法查看正文。
- 封存后，无论写信人还是伴侣，都无法通过页面或接口取得正文。
- 修改设备时间不能提前解锁信件。
- 到达服务端开启时间后，双方都可查看完整内容，并各自记录首次阅读时间。
- 解锁通知只发送一次，不因刷新或重复任务而重复发送。

## 10. 非功能要求

### 10.1 安全

- 所有数据查询和修改均校验情侣空间成员身份，不能只依赖前端路由保护。
- 关键余额操作使用数据库事务、幂等键和行级锁，防止并发重复执行。
- 图片上传限制文件类型、尺寸和访问权限。

### 10.2 性能

- 首页快捷入口加载不应依赖三个模块的数据接口。
- 列表默认分页，每页建议 20 条。
- 常用列表查询目标响应时间不超过 2 秒；提交操作应提供加载状态并防止重复点击。

### 10.3 可用性与无障碍

- 颜色不能作为状态的唯一表达，必须同时提供文字或图标。
- 弹窗支持键盘操作和明确焦点。
- 表单错误显示在对应字段附近，并保留用户已填写内容。
- 所有成功、失败和审批结果均有清晰反馈。

### 10.4 数据留存

- 订单、甜心币流水和审批记录不得由普通用户物理删除。
- 打卡和未来信件优先采用软删除或双方确认删除。
- 旧账单数据在用户确认清理方案前保持归档，不参与新功能余额计算。

## 12. 本稿采用的默认方案与待确认项

为便于先形成可开发需求，本稿采用以下默认方案；进入设计或开发前建议最终确认：

1. “甜心币”和“金币”视为同一种虚拟币，产品名称统一为“甜心币”，使用金币图标。
2. 双方各自拥有独立余额；点单只扣下单人的余额。
3. “双方同意加币”采用一方发起、另一方审批的方式；发起行为视为发起人已同意。
4. 菜单由双方共同维护，订单由商品提供者接单和完成。
5. 打卡评价不是盲评，一方提交后另一方可立即看到。
6. 未来信件由一人撰写；封存后连写信人自己也不能查看正文，直到时间到达。
7. “到时间开启后双方才能查看”指到期后两人都获得查看权限，不要求两人同时在线或共同点击开启。
8. 原账单从产品中下线，但历史账单数据先归档保留，不直接删除。

## 13. 整体验收场景

1. 用户从首页“我们的日常”进入三个新模块，且不再看到“恋爱账单”。
2. A 为自己申请 50 枚甜心币，填写理由；B 同意后 A 余额增加 50，双方可查看完整流水。
3. A 用自己的甜心币点单，余额正确扣除，A 看到成功提示，B 收到新订单通知。
4. B 拒绝订单后，A 的甜心币自动退回，扣币和退款都有记录。
5. A 创建一家餐厅打卡并评价，B 收到通知并提交自己的评价，详情正确展示两份评价和平均分。
6. A 写一封未来信并封存；到期前 A、B 通过任何正常页面或接口都无法获取正文。
7. 到达设定时间后 A、B 均收到通知并可阅读信件，各自首次阅读时间被正确记录。
